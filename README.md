## Instagram stats

The hero, audience charts, and Instagram Performance section share `/api/instagram-stats`. Account stats refresh through the Supabase worker **once daily at 9:30 PM IST (16:00 UTC)**. The website reads only saved Supabase data and never calls Meta because of a page visit, including when `INSTAGRAM_ACCESS_TOKEN` is present locally. Saved snapshot and Story aggregate reads are cached for five minutes to reduce database traffic; this cache does not control Meta collection. Story collection runs separately once per hour.

The route reads the last successful Supabase snapshot using `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. The snapshot retains its original update timestamp, and a failed scheduled sync does not replace it. Performance shows an unavailable state until a snapshot with real performance metrics exists; it never falls back to illustrative values. The Meta credential stays in Supabase Vault. The optional server-only `INSTAGRAM_ACCOUNT_ID` filters the saved Story aggregate; the frontend does not need an Instagram access token.

The performance switch sits below Accounts engaged, aligned with “Stories worth stopping for.” **Lifetime** is selected on every visit; **30 days** switches instantly using the same API response. Lifetime likes and comments use actual counts across all currently published posts. Average likes/comments use all published posts in Lifetime and only posts published within the last 30 complete UTC days in 30 days. These averages use current lifetime counts on the selected posts, not interactions received during that window. Follower engagement follows the same selected-post averages. Missing timestamps or incomplete media pagination leave recent averages unavailable; no posts in the window also leaves averages unavailable. Lifetime views, interactions, saves, shares, profile visits, and profile-link taps use available tracked history, with its coverage dates displayed below the metrics. This is not a verified account-lifetime total. Total views is the large headline stat and follows the selected period. Accounts reached appears in the first metric row and is explicitly labeled “30 days” in both periods; Engagement rate and Accounts engaged also always use the last 30 complete UTC days. Their tooltips identify the window. A direct 90-day reach request was verified against this account and rejected by Meta with code 100: “There cannot be more than 30 days (2592000 s) between since and until.” Unique reach/accounts engaged cannot be summed across shorter windows without double counting, so neither a 90-day nor a January 7-to-present unique reach total is estimated. Bio-link clicks use the existing, separately dated click archive for Lifetime and a direct matching 30-day query for 30 days.

The Reels section below the two account metric rows always uses lifetime data, independently of the period switch. `snapshot.reels` contains average views and average accounts reached per published reel, the arithmetic mean of Meta's per-reel average watch times in seconds, and summed lifetime watch time including replays in hours. The sync reuses the complete, deduplicated media traversal and fetches insights only for `media_product_type=REELS`, with bounded concurrency. Watch times are converted from milliseconds. The Reels row displays average views, average reach, average Story views, and total watch time; average watch time is retained in the snapshot but is not displayed. Missing reel membership or incomplete media pagination leaves all reel metrics unavailable; a missing per-reel insight leaves that aggregate unavailable instead of displaying a partial value. Redeploy the worker when updating these fields; they appear on the site after the next successful sync.

The same row shows **Avg Story Views**, independently of the account period switch. A separate lightweight `sync-instagram-stories` Edge Function collects active Story IDs, publication timestamps, and views **once per hour**. It reuses the existing Vault credential and sync secret without fetching account insights, media lists, or historical backfills. `instagram_story_views` stores one private row per Story, updating its last successful count rather than adding hourly totals. Failed/empty insights preserve the last successful value; a reported zero stays zero. After a Story is 24 hours old, its last recorded views enter the stored average in `instagram_story_averages`. Until completed data exists, the UI shows the separate average of available active-Story counts; its tooltip explains that these Stories are still gaining views. Completed history takes priority as soon as it exists, and active counts never enter that historical average. Only the aggregates are publicly readable. The API returns `storyAverage: { views, count, scope, observedAt }`, where `scope` is `active` or `completed`, separately from the account snapshot. This historical average has no five-minute expiry. There is no extra visible date or tracking text. With no available active or completed counts, the average is unavailable.

Meta only exposes Story insights for 24 hours, so hourly polling records an approximation of the final count and cannot reliably backfill expired Stories. The legacy `snapshot.stories` field remains compatible but is no longer displayed. See [Meta’s media insights reference](https://developers.facebook.com/documentation/instagram-platform/reference/instagram-media/insights).

To enable hourly Story collection in the existing Supabase project:

1. Apply [the Story storage migration](supabase/migrations/20261108000000_instagram_story_views.sql) and then [the active-average migration](supabase/migrations/20261108010000_instagram_active_story_average.sql) in the Supabase SQL Editor, after the original mediakit migration. The second migration also populates the active fallback from existing observations.
2. Deploy with `npx supabase functions deploy sync-instagram-stories --remote=<project-ref> --use-api`. This needs an authenticated Supabase CLI; no new token, service key, or Vault entry is required on the deployed function.
3. Apply [the hourly schedule](supabase/schedule-instagram-stories.sql) in the SQL Editor. It uses the existing `instagram_mediakit_project_url` and `instagram_mediakit_sync_secret` Vault entries and leaves the daily account sync alone. The named job is replaced if this schedule is reapplied, rather than duplicated.
4. Verify `instagram-story-sync` in Cron history and the rows in `instagram_story_averages` after collection begins. To start immediately, invoke the function with the existing `x-instagram-sync-secret`; otherwise wait for the next hour.

Hourly collection uses 24 scheduled invocations per day (672–744 per month), plus any manual invocations. No per-visitor Edge Function calls, Realtime subscription, hourly history rows, or additional account backfill is added. The UI reads a cached single-row aggregate. The SQL behavior and RLS checks in [the storage regression script](tests/instagram-story-storage.sql) run on a disposable PostgreSQL database after applying the Story migration and roll back their test data.

Snapshots now include schemaVersion: 3, defaultPerformancePeriod: "lifetime", and separate performancePeriods.lifetime / performancePeriods.last30Days objects. The legacy performance, hero views, and audience data remain compatible. The worker saves performance.performanceHistory alongside the existing bio-link archive in the existing JSONB snapshot, so no SQL migration is required. The initial performance backfill covers the last 90 complete UTC days in non-overlapping windows of at most 30 days. Later syncs retain older windows beyond API retention, replace recent windows to account for revisions, and retry missing metrics. Unavailable or stale windows never become zero or a partial historical total. Deploy the updated sync-instagram-stats worker and run one sync to begin persisting this archive; only the scheduled worker refreshes and persists the archive. Older snapshots still support the 30-day view and show Lifetime as unavailable until refreshed.

The **30 days** option covers the last 30 complete UTC days. Unique reach and accounts engaged come from Meta's window totals; daily unique reach is retained in the snapshot and is never summed to estimate window reach. Engagement rate is calculated as accounts engaged / accounts reached × 100, and is unavailable when reach is zero or either metric is missing. Likes and comments are period totals, not per-post averages. Views replace deprecated impressions. Profile link taps use `profile_links_taps`, not a claimed count of bio clicks. The first desktop metric row contains likes, accounts reached (30 days), saves, and shares. The second row contains total interactions, profile views, average likes, and bio-link clicks. Each row uses four columns on desktop and two on smaller screens. Total comments and average comments are retained in the snapshot but are not displayed. Follower engagement is retained in the data but is not displayed. Avg Likes and Avg Comments use current lifetime counts on published media returned by the paginated media endpoint, filtered by publication timestamp in the 30-day view; carousel containers count once. Follower Engagement = (Avg Likes + Avg Comments) / current followers × 100. Missing/hidden counts, incomplete pagination, or unavailable media leave the affected averages unavailable. A missing likes count does not invalidate an otherwise complete comments average. Profile views use a separate optional `profile_views` request with `metric_type=total_value` over the same 30-day window. Bio link clicks (tracked total) use `website_clicks` totals over consecutive, non-overlapping UTC windows of at most 30 days. Both were verified against this account; the old time-series deprecation does not mean these total-value requests fail. These optional metrics are isolated from core performance because the published account reference omits them. An initial backfill covers the available history (two years, with one day of boundary margin). Later worker syncs preserve historical windows in the existing Supabase JSON snapshot, replace recent windows to pick up delayed/revised counts, and retry missing windows. Saved windows survive aging out of the API retention period. Empty/error results stay unavailable and never become zero or a misleading partial total. The UI labels this a tracked total and gives its date coverage in the tooltip; it is not a verified account-lifetime count. No manual count environment variables are used. Redeploy the existing worker when updating this code so daily syncs persist the click archive; the Next.js route reads the saved snapshot, while only the authorized worker fetches and publishes updates. Missing metrics stay unavailable, while a reported zero stays zero. No illustrative values are used for either period. Meta can delay insights by up to 48 hours. The audience charts use follower demographics reported by Instagram. See [Meta's account insights reference](https://developers.facebook.com/documentation/instagram-platform/api-reference/instagram-user/insights).

The Supabase worker publishes the daily snapshot so the site keeps its last successful data when Meta is unavailable. To configure this scheduled path:

1. In the [urmi-mediakit app dashboard](https://developers.facebook.com/apps/1096130900092084/), open **API setup with Unified login**. Use a configuration with `instagram_basic` and `instagram_manage_insights`. Authorize `@uwummie` and generate a token. [Meta's Unified Login guide](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-unified-login/get-started)
2. Apply the migration with the Supabase CLI or SQL Editor. In Supabase Vault, create a secret named `instagram_mediakit_token`. Store a JSON object with `accessToken` and `accountId` (the Instagram account ID as a string). Include `expiresAt` as an ISO 8601 timestamp if Meta provides an expiry. Keep the token in Vault or a gitignored local file during setup.
3. With Supabase CLI v3, deploy using `npx supabase functions deploy sync-instagram-stats --remote=<project-ref> --use-api`. Set `INSTAGRAM_SYNC_SECRET` under Edge Function secrets to a random 32-byte hex value. In Vault, add the same value as `instagram_mediakit_sync_secret` and the Supabase project URL as `instagram_mediakit_project_url`.
4. Send a `POST` to `<project-url>/functions/v1/sync-instagram-stats` with the `x-instagram-sync-secret` header. Check the function logs and verify the snapshot at `/api/instagram-stats` against the Instagram dashboard for the matching window. Run [the scheduling SQL](supabase/schedule-instagram-sync.sql) in the SQL Editor after verification. Supabase Cron runs the function every day at **16:00 UTC (9:30 PM IST)**. Reapplying this named job updates its schedule rather than adding another job.

The worker uses the configured Unified Login token until Meta expires or revokes it. Reauthorize the account and update the Vault entry if that happens. Existing Instagram Login entries with `accessToken` and `expiresAt` still refresh automatically when 14 days or fewer remain. Each failed run leaves the previous snapshot available. Check Edge Function logs for sync failures.

A token can have `instagram_manage_insights` granted while still having no Instagram account assigned to it. In that case `/me/assigned_instagram_accounts?fields=id,username` returns an empty `data` array. Check the Instagram asset shared through the Unified Login configuration and its business portfolio. The account ID is not the system user's `/me` ID. If you already have the Instagram professional account ID, set `INSTAGRAM_ACCOUNT_ID` to query it directly; the worker still validates that the returned username is `uwummie` before requesting insights.

Stories in motion uses `reels.showcase` from the saved snapshot: five most recent reels above the heading and five most popular by lifetime views below it. Published thumbnails and permalinks come from Meta's media endpoint, using the existing media traversal and reel-insight requests. Redeploy `sync-instagram-stats` and invoke it once to populate this field; no database migration or new credential is required. Daily syncs refresh the selections and signed thumbnail URLs. Featured Works remains a separate sample gallery.
